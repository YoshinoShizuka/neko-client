# 取满手势：五轮真机事故与排障手册

> 这篇记录 `取满手势`（按住组合键 + 点仓库格 → 取出到背包放不下为止）从 0.2.0 到 0.4.7
> 的完整踩坑过程。README 只留使用说明，**细节、真机日志证据与排障表都在这里**。
> 服务端行为见 `carpet-Neko-Addition` 的 `docs/出料漏斗满盒分类物刷物品事故与修复.md`。

## 时间线（每一条都有真机日志作证）

### 0.2.0：手势落地，组合键写死

`Ctrl + Alt + 左键` 在 `mouseClicked` 的 HEAD 判断，命中就 cancel 原版点击、改发
`carpet_neko_addition:fill_request{slotId}`。原版容器的点击协议里**没有修饰键**
（`PICKUP / QUICK_MOVE / SWAP / CLONE / THROW / QUICK_CRAFT / PICKUP_ALL` 一个都带不了
Ctrl / Alt），所以这个手势只能在客户端识别。

### 0.3.0：换成 malilib，为什么必须换

原版按键绑定只在 `Minecraft.screen == null` 时派发，而这两个键恰恰都是**在仓库界面里**按的
—— 用原版绑定等于永远按不出来。malilib 的热键带 `Context`，这里取 `ANY`（游戏内 + 界面都响应），
同时设 `cancel=false`，所以搜索框聚焦时按热键仍然是正常打出字符。

### 0.4.3：组合键可配置，然后彻底不生效

把组合键做成配置项 `keyFillCombo`，却用 `KeybindMulti.isKeyDown` 去查「某个键按着没有」。

26.x 的 malilib 把 **SDLK**（`LEFT_CONTROL` = 1073742048）当成 SDL 的 **scancode**（0..511）
去索引 `SDL_GetKeyboardState()` 的裸内存视图 —— 越界**不抛异常**，读到 0 ⇒ 恒 false。
`isKeybindHeld()` 同样不可用：它的 `pressed` 由 `PRESSED_KEYS.containsAll(scanCodes)` 算出，
而 `PRESSED_KEYS` 每帧都被同一个坏 API 清空。

### 0.4.4：改用点击事件的修饰键快照，仍然没反应

改问 `MouseButtonEvent.hasShiftDown() / hasControlDown() / hasAltDown()`（原版 Shift 快速移动
读的就是它）。但真机复测还是「按了没反应」：日志里唯一一条判据快照是

```
按钮=3 → 键码=-97 绑定鼠标键=-99 … 命中=false
```

而且那条日志**只打一次**（`firstModifierClickLogged` 只放行第一条），之后真正的点击一个字都没留下。

### 0.4.5：三处硬修 + 一条错误设计

修对了三件事：

1. **槽位按点击坐标现算**。原版 `AbstractContainerScreen#isHovering` 是「四周各 1px 宽容框」
   （`x-1 .. x+17`），而 `hoveredSlot` 是渲染帧写的、可能滞后一帧 —— 改成
   `getHoveredSlot(event.x(), event.y())` 现算，删掉 `hoveredSlot` 字段。
2. **`warehouse` 目录标志从「动作通道硬门禁」降级成视图标志**。服务端
   `FillNetwork#handleFill` 本来就自己校验 `voidWarehouse` 规则 + `VoidWarehouseMenu`，
   客户端不该越权拦截。目录未到 = 补发 hello + 请求照发 + 不吞原版点击。
3. 整条链路的静默 `return` 全换成带原因的日志。

同时引入了**一条错误设计**：`MOUSE_BUTTON_TOLERANCE = 2` + `matchesTolerantMouse(...)`
—— 绑了修饰键时，键码差 ≤2 就算命中。

真机确实开始 `已取出 …` 了，但日志连续十几次写着

```
按钮=3 → -97 … 命中（按钮号容错 ±2）  →  已取出 44,928 个 …
```

玩家绑的是 `Ctrl+Alt+左键`，真正生效的是**右键**。反馈原话：

> 实际生效的不是 Ctrl+Alt+左键 而是 Ctrl+Alt+右键

**功能能用 ≠ 语义正确。** 隐性容错等于偷偷替玩家改配置，比静默失效更难查。

### 0.4.6：撤销全部容错

判据只剩一条严格匹配：`绑定键码 == 原版按钮号 − 100`。

- 删掉 `MOUSE_BUTTON_TOLERANCE` / `Combo.hasModifiers()` / `matchesTolerantMouse(...)`；
- 新增纯方法 `modifiersMatch(...)`，把「按钮号不符」与「修饰键没按全」分开报；
- 未命中日志直接写「点的是键码 X，绑定的是 Y」，并附上当前 `组合键=<显示串>`；
- **日志分级**：判据 / 状态走 `trace`（40 行 burst + 1/s），`取满发包*` / `取满中止*` /
  `取满降级` / `取满链路` 走 `audit`（独立 200 行预算）。0.4.5 的判据行曾把
  `取满发包成功` 挤出日志（22:48:15 命中、22:48:16 已取出，中间没有发包成功行）。

### 0.4.7：默认改成右键 + 区域诊断

真机复测结论：「左键绑定不生效，右键绑定有效」。但**根因不是按键**。

0.4.6 日志里左键那三次都是 `命中（精确）` 紧跟 `取满中止：点击坐标 … 没落在 0..45`。
按真机 `guiScale:3` / `leftPos≈339` / `topPos≈129` 把绝对坐标换算成界面相对坐标：

| 绝对坐标 | 相对坐标 | 实际落在哪 |
| --- | --- | --- |
| (470.18, 275.0) | relY ≈ 146 | **玩家背包** |
| (472.52, 290.33) | relY ≈ 161 | **玩家背包** |
| (421.50, 345.67) | relY ≈ 216 | **快捷栏** |

取满只认**前 5 行内容格**（服务端 `PAGE_SIZE = 9×5 = 45`、`NAV_START = 45`，
第 6 行是导航行）。所以「左键失效」其实是**瞄错了格子**。

两项改动：

1. `DEFAULT_KEY_FILL_COMBO = "LEFT_CONTROL,LEFT_ALT,BUTTON_2"`（Ctrl+Alt+右键）。
   **只影响新生成的配置**，已有 `keyFillCombo` 绝不改写。
2. `slotAt() == null` 时不再只报「不在内容格」，而是打出界面原点、相对坐标和**区域名**。

## 为什么组合键是「一个鼠标键 + 三个修饰键」

原版只对外暴露 Shift / Ctrl / Alt 这三位修饰键的实时状态。绑字母 / 数字键时无法在点击那一瞬间
判定 —— 这类绑定会被判「组合键不可用」，并在进服日志里写明是哪个键，**绝不静默失效**。

配置里存的是**键名**（`BUTTON_1` / `MOUSE_RIGHT`），由各版本 malilib 自己解析成该版本的码值：

| 版本 | 左键 | 中键 | 右键 |
| --- | --- | --- | --- |
| 26.3（1 基，`BUTTON_1/2/3`） | `-99` | `-98` | `-97` |
| 26.2 / 26.1.2 / 26.1.1（0 基，`MOUSE_BUTTON_1/2/3`） | `-100` | `-99` | `-98` |

点击事件用同一套编号 ⇒ **严格匹配跨版本天然自洽，版本差不需要任何容错**。

## 「按了没反应」怎么自查

进服后日志会打印 `取满组合键=…（判定：可用 / 不可用：原因）`。之后**每一次带修饰键的点击**
都会留一行 `取满判据：按钮=… 键码=… 绑定鼠标键=… 组合键=… Shift/Ctrl/Alt=… ⇒ 命中 / 未命中：原因`。

| 日志里看到 | 结论 |
| --- | --- |
| 完全没有 `取满判据` 行 | 点击没进判据（开关关了 / 点击被别的模组先吞），先查 `fillGesture` |
| `组合键=不可用：…` | 绑定里混了字母键 / 没有鼠标键 / 有多个鼠标键，按提示改绑定 |
| `未命中：绑定的修饰键没按全` | 点击那一瞬间的修饰键掩码没读全（键盘侧问题） |
| `未命中：点的是键码 -99，绑定的是 -97` | **点错鼠标键了**。判据严格匹配，这是设计行为；想换键就改 `keyFillCombo` |
| `取满中止：… 区域=玩家背包（不是仓库内容格）` | 点到自己背包上了；取满只认前 5 行内容格 |
| `取满中止：… 区域=快捷栏` / `区域=第 6 行导航行` | 同上：快捷栏和导航行都不是取满目标 |
| `取满中止：… 区域=内容行内、但不在任何一列上` | 点在列间空隙 / 边框上，微调落点 |
| `取满发包失败：… canSend=false` | 对端没装配套服务端 mod 或通道没注册 |
| `取满降级：目录未到` | 目录握手还没回来；请求仍会发出、这次点击退回原版「取 1 个」 |
| 判定行里的「组合键=…」和你以为的不一样 | 配置被改过 / 还没重进世界；手改 json 必须退出重进一次世界 |

## 通道撞名与 0.4.0 那次断线

Fabric 的 payload 注册表按通道 id 严格去重，「谁能编码这个 id」取决于**先注册那一方**
塞进去的 codec。所以注册完之后客户端会回头核对一次归属：把这个 id 名下登记的 codec 取出来，
跟自己的 `CODEC` **比引用**。

| 局面 | 日志 | 行为 |
| --- | --- | --- |
| 专用服务器（两边两个 JVM） | 无 | 自己注册成功，正常 |
| 单人存档（服务端 mod 先注册同一个类） | `WARN … 已被先注册，归属核对通过` | 正常 —— 单人里这条 WARN 是**常态**，不是错误 |
| 撞名的是**另一个类**（别的模组占了 id / 两端版本不配套） | `ERROR … 名下登记的不是本模组的 codec` | 该功能**自行关闭**，一个字节都不发；`WARN 通道自检未通过` |

🔴 为什么必须「发之前」拦：这类不匹配引发的异常发生在 **netty 线程**上（编码阶段 cast 失败），
`try/catch` 根本碰不到，玩家只会看到断线。宁可搜索框不出现、取满手势退回原版「取 1 个」，
也不许把客户端踢下线。

**0.4.0 就是踩了这个坑**：把四条通道的 payload 类也一起挪进了 `neko.client`，而服务端 mod 里
还有一份同名的旧包版本 —— 单人存档两端同进程，注册表里躺着的是**服务端那个类**的 codec，
客户端却发自己类的实例，编码时 cast 失败：

```
Can't encode 'SearchHelloPayload[]', expected 'SearchHelloPayload[]'
```

两个类同名不同包，报错看着一模一样 ⇒ **一开仓库界面就断线**。0.4.1 把那四个类搬回
`neko.voidwarehouse.*` 并与服务端**逐字节对齐**（判据 = 两个 jar 里同名 `.class` 比 md5）。

## 版本差异与两个只此一家的编码坑

| 差异点 | 26.x | 1.21.11 |
| --- | --- | --- |
| 网络注册 | `serverboundPlay()` / `clientboundPlay()` | `playC2S()` / `playS2C()` |
| 渲染注入 | `extractRenderState(GuiGraphicsExtractor,...)` TAIL 后手动 `box.extractRenderState(...)` | `render(GuiGraphics,int,int,float)` TAIL 后手动 `box.render(...)` |

两代容器屏都不渲染 renderables（javap -c 实证：都不调 super），搜索框都必须手动驱动。
其余源码五版本逐字节相同（换行统一 CRLF）。

> 🔴 0.2.0 时这里还有第 3、4 项（Fabric 按键 API 模块改名、动作栏消息方法分叉），0.3.0 换成
> malilib 后**两项一起消失了**：注册热键由 `InputEventHandler` 管，动作栏提示走
> `InfoUtils.printActionbarMessage` —— 少一个分叉文件 `SearchPlatform.java`。

> 🔴 26.3 有两处**只此一家**的编码，写死另一版本的值会静默失效：
> `InputConstants.Type` 常量改名为 `KEYBOARD`（1.21.11 叫 `KEYSYM`）⇒ 不碰它，热键全交给
> malilib 的存储串；`Minecraft#screen` 在 26.1.x 是公开字段、26.2+ 挪到 `Gui#screen()` ⇒
> 干脆不碰，界面刷新由 mixin 实现 `SearchScreenAccess` 把宿主屏存下来，配置界面由
> `GuiBase.openGui` 打开。

## 附：配方本为什么一直「正在向服务端要配方本…」（0.4.8 → 0.4.9）

0.4.8 的配方本界面打开后**永远**停在那一行，而单测 57 条、jar 断言 973 条全绿。

### 真因：服务端在闸门没过时**静默 return**

`RecipeNetwork` 的闸门当时有三道：规则开着、**玩家正开着自己的仓库界面**、权限。任何一道没过，
服务端都是 `return`，**一个回包都不发**（有意不向可疑客户端确认通道存在）。而热键是玩家在野外按的
—— `containerMenu` 是原版背包菜单，第二道必然不过。客户端把「没回包」当成了「还在等」，于是无限转圈。

### 🔴 更正：那道「必须开着仓库界面」已经不存在了

0.4.9 第一版顺着「服务端只认开着的仓库界面」这个前提，在客户端加了 `NEED_CONTAINER` 态：
`containerMenu instanceof InventoryMenu` ⇒ **连 hello 都不发**，只写一句「先开仓库」。
**这个前提在服务端 1.0.17 就已经取消了**（`cce513f`：`openedMenu` → `dataOf`，只判
`craftEnabled()` + 数据能不能取到）。于是客户端那条判断只剩一个效果：**把一个本来会成功的请求
挡在客户端** —— 玩家在世界上按热键，服务端会回，客户端却不问。

⇒ 结论：`NEED_CONTAINER` 整个删掉，判据只留一条「发出去，等 2 秒」。教训不是「别做前置判断」，
而是 **客户端不许替服务端设限**：能问就问，让对端自己回答。

### 现在的形态（0.4.9）

| 处境 | 怎么判 | 界面说什么 |
| --- | --- | --- |
| 正在等回包 | 已发 hello | 「正在向服务端要配方本…」 |
| 服务端不回 | 2 秒超时（服务端同步回包，正常几十毫秒） | 「需要 1.0.17+，且 `voidWarehouse` / `voidWarehouseCraft` 都开着」+ 重试按钮 |
| 对端没有这条通道 | `canSend` 为 false | 热键只闪动作栏提示，不开空界面 |

翻页也有同样的坑（服务端丢包 ⇒ 页码不动、列表不换），所以 query 也带 2 秒超时，
且**页码只认回包**（以前是本地先改 `page`，服务端不回时界面会显示「第 2 页」而内容是第 1 页）。

### 一个只有真跑才会撞到的细节：按钮建得比状态早

「重试」按钮原本写着 `if (phase == NO_REPLY)` 才 add，而 `NO_REPLY` 要等 2 秒超时才出现、
按钮只在 `initGui` 里建 ⇒ **永远建不出来**。改成恒在（正常浏览时点它 = 重新要一次索引）。

### 第二轮真机（同名 0.4.9 原地重建）：标题叠字 + 列表空白

1. **标题和状态行叠在一起**：malilib `GuiBase#drawTitle` 把标题画在 **(20, 10)**（常量 `LEFT=20 / TOP=10`），
   而状态行写在 (12, 14) —— 只差 4 像素，真机上「配方本」和「已用 15 / 2048」直接叠成一团。
   ⇒ 文本列统一到 x=20（与标题同列），状态行 y=22、回执行 y=33、提示行 y=44 起，列表顶边 44。
   **教训**：用别人的界面基类时，先 `javap` 看它把标题画在哪，再决定自己的第一行写在哪。
2. **「共 15 条 / 第 1 / 2 页」但一行都没有**：`onIndex` 收完 `recipe_index` 只填了元信息
   （`total` / `used` / `outputs`），**从没去要一页明细** —— 条目在 `recipe_page` 里，不在索引里。
   ⇒ `onIndex` 末尾接 `requestPage(page)`；另加 `ensurePageLoaded()` 兜底
   （READY + `total>0` + 第一页空 + 无在途请求 ⇒ 最多补要 2 次，仍空则写「没能取到这一页」）。
   **教训**：「元信息到了」不等于「内容到了」，凡是分两包给的接口，都要有一个「内容迟迟没来」的兜底。

### 第三轮真机（同名 0.4.9 再重建）：数据到了，控件里却是空的

现象：标题写着「共 15 条 / 第 1 / 2 页」，列表一行都没有；**日志里一条异常都没有**
（只有 11 条通道注册成功的自检行）。

定位链（全是 `javap` 读 malilib 读出来的，不靠猜）：

1. `WidgetListBase` 把条目存在**自己的** `listContents` 里，绘制遍历的也是它；
2. 往 `listContents` 灌数据的只有 `refreshBrowserEntries()` ← `refreshEntries()` ←
   **`WidgetListBase#initGui()`**（全类唯一调用点）；
3. `GuiListBase#initGui()` 会替我们做 `setSize + initGui` —— 但这只对**已存在**的控件生效；
4. 我们的 `reCreateListWidget()` 是在 `GuiListBase.initGui` **之后**才调用的（数据变了才重建），
   于是新控件永远拿不到 `initGui()` ⇒ `listContents` 一直是空 List ⇒ 画 0 行。

修法：`applyHintLayout` 里重建之后补上 `setSize(bw, bh)` + `initGui()` + `resetScrollbarPosition()`，
与 `GuiListBase.initGui` 完全同序。另外给 `RecipeClientState` 加了审计日志
（`[recipe] index: total=… / page 0: 8 条 / delete result: status=…`）——
这次的教训是「界面空白 + 日志干净」等于没有线索，所以以后这条链路必须自报数。

**两条教训**：

1. 用别人的界面基类，**重建控件时必须走它自己的初始化序列**（构造 → `setSize` → `initGui`）。
   只 `new` 一个出来，它内部缓存是空的，而且不会报错。
2. **「数据到了」和「界面画出来了」是两件事**：上一轮加的 `ensurePageLoaded()` 只保证前者，
   这次的故障在后者。凡两端之间的转换，验收要各咬一次。


## 附：0.5.0 为什么把翻页改成滚动，又加了搜索与图标

> 这是**主动重做界面**，不是事故修复。但三个决定各自都有一条真机/协议上的硬理由，留档避免以后被"简化"掉。

### ① 翻页 → 连续滚动

0.4.x 一页 8 条，137 条的本子要按 18 次「下一页」——玩家不是在找配方，是在猜页码。
协议本身是分页的（`MAX_PAGE_SIZE = 32`），所以没有改服务端：**客户端把页累进一个池**，
滚到还剩 `PREFETCH_ROWS = 6` 行时自动要下一页。三条判据必须同时成立，缺一个就是「滚到底不动了」：

1. `WidgetListRecipe#createListEntryWidget` 把 `listIndex` 报给 `RecipeClientState.noteVisibleRow`
   （malilib 只为**可见**行建控件，这个下标天然就是视口底部；不读滚动条字段是因为 1.21.11 会 remap 成 `field_xxxx`）；
2. `RecipeBrowseModel.shouldPrefetch(lastVisibleRow, loaded, total)` 判定是否接近池底；
3. `RecipeClientState.prefetchIfNeeded()` 在 `pendingQueryAt == 0` 时发下一页，且用服务端回的 `page + 1`
   而不是本地算 —— 两次请求之间别人学/删了一条，服务端的分页窗口会滑动。

追加时按 `recipeId` 去重，否则窗口一滑就会出现同一条显示两遍。

### ② 搜索：为什么不是本地筛选

0.4.x 明确写过「没有文本搜索」，当时是把搜索框关掉的（`hasFilter() = false`），理由只有一条：
malilib 自带的过滤只能筛**当前页 8 条**，玩家搜第 9 页的东西会被判「没有这条」——比没有搜索更糟。

0.5.0 的做法是把 malilib 的搜索框**装回来**（`widgetSearchBar` 是 `WidgetListBase` 的 protected 字段，
由子类 new；malilib 自己负责绘制、键盘、输入法），但同时重写 `entryMatchesFilter()` **恒返回 true**：

> 🔴 搜索词只用来驱动服务端重查，不用来筛控件。否则就会出现「服务端按 id 命中、本地按名字筛不到」
> 的隐性双重过滤，玩家看到的是列表莫名其妙少了几条。

链路：输入框原文（每帧轮询，事件类型跨版本不同，不碰）→ 250 ms 防抖 →
`RecipeBrowseModel.matchRank` 在**客户端**按本地化名字/id 给 `index.outputs` 打分 →
产物 id 白名单随 `recipe_query.outputs` 发给服务端 → 结果按匹配度重排置顶。

三个坑：

- **服务端只认 id**：它没有 `zh_cn.json`，「铁锭」在服务端没法对上号。名字匹配必须在客户端做。
- **空名单 ≠ 没结果**：服务端把空数组定义成「不过滤」。搜到 0 个产物时如果在客户端不拦住，
  就会把整本发回来，表现为「搜索根本没生效」。现在直接置空列表并说「没有匹配的配方」。
- **重建控件会吃掉输入**：0.4.9 的修法是「数据一变就 `reCreateListWidget + initGui`」，
  那会让玩家打字打到一半时输入框变空、滚动条回顶。0.5.0 改成：只有版面变化才重建；
  数据变化只调 `list.refreshEntries()`（public，做的正是装数据那一步），并给新控件回填 `filterText`。

### ③ 图标：两代渲染入口其实有一条公共线

一开始判断「画图标要把界面拆成两套代码」——26.x 是 `GuiGraphicsExtractor#item(...)`，
1.21.11 是 `GuiGraphics#renderItem(...)`。后来 `javap` 发现 malilib 的 `GuiContext` 恰好抹平了：

- 26.1.2 / 26.2 / 26.3（0.28.12 / 0.29.6 / 0.30.1）**自己声明了** `renderItem(ItemStack,int,int)`
  与 `renderItemDecorations(Font,ItemStack,int,int)`；
- 1.21.11（0.27.20）的 `GuiContext extends class_332`（GuiGraphics），两个方法**从父类继承**。

所以 `ctx.renderItem(stack, x, y)` 一行在五个版本都能编译、都能画，列表行文件仍然五版本逐字节相同。
名字也走 `SearchCatalogResolver.nameOf()` 兜底：解析不出来时退回 id 的 path，
否则「客户端不认识这个物品」的那条配方会从搜索和排序里一起消失。

### 验收与变异

- 单测 **74 条**（原 61 + 匹配度 6 + 预取 3 + 防抖 3 + 状态行 1）；jar 断言 **1168 条**。
- 变异六次：删掉行号上报 / 加回翻页按钮 / 删掉 `entryMatchesFilter` / 不画图标 / 整块删防抖 /
  对调匹配度两级 —— 全部变红。
- ⚠️ 诚实记录一条局限：字符串级断言只能咬住「调用链在不在」，咬不住「函数体是不是空实现」。
  把 `noteVisibleRow` 改成空函数、或把 `entryMatchesFilter` 改成 `return false`，jar 断言仍然全绿
  （单测也覆盖不到）。这类变异只能靠真机滚动/搜索来验。


## 附：0.5.1 模糊拼音与「一次显示多少条按屏幕现算」

### ① 模糊拼音：归一化，不展开变体

拼音/首字母 token 复用 common 的 `SearchIndex`（与仓库搜索框同一个词库、同一条误差口径），
新增的一步是 `RecipeBrowseModel.fuzzyKey`：把容易混的读音折到同一个键上，**查询串与 token 两边都折**，
之后就是普通字符串比较。

| 组 | 折法 |
| --- | --- |
| 翘舌 | `zh→z`、`ch→c`、`sh→s` |
| 前后鼻音 | `ing→in`、`ang→an`、`eng→en` |
| 声母混读 | `r→l→n`（n/l/r 一组）、`f→h` |

两个顺序坑（单测 I1 咬住了）：

1. **双字先折**：`zh` 必须在单字之前，否则先被拆成 `z`+`h`，`zhang` 会折成错的键；
2. **`r→l` 必须在 `l→n` 之前**，否则 r 折不到 n 上（n/l/r 三字要落到同一个键）。

代价（接受的误差）：`日/热` 与 n 组互串、`方/行` 与 `黄` 的韵母互串 —— 真实输入法的模糊音就是这么设计的。
挡位顺序：拼音命中排在 id 命中**之前**（对中文用户更有用），排在名字命中**之后**（直接打中文仍最准）。

为什么不「把查询展开成变体再逐个试」：归一化是 O(n) 一遍字符串替换，展开是组合爆炸
（每组 ×2，七八组就是上百个变体），而且两边都要展开一遍才能比。

### ② 一次显示多少条：按屏幕现算

0.5.0 里预取裕量写死 6 行，大屏（比如可见 30 行的窗口）滚到底会出现「停下等包」。
0.5.1 的判据是：

- 界面每帧算 `可见行数 = 列表高度 / 行高`，塞给状态机（`setVisibleRows`）；
- 裕量 = `max(PREFETCH_MIN_ROWS=4, 可见行数 / 2)`；
- 行高只有一个来源 `RecipeBrowseModel.ENTRY_HEIGHT` —— 界面换算与列表行高共用同一个常量，
  两边各写一个 24，改了一边就会出现「裕量算错」这种最难查的偏差。

🔴 javap 断言里的坑：`ENTRY_HEIGHT` 是编译期常量，**调用处会被 javac 内联成字面量 24**，
所以在 jar 里咬不到 —— 只能在声明处（`RecipeBrowseModel.class`）咬字段，外加咬
「界面确实调了 `setVisibleRows`」。这条还配了变异：删掉界面的报告调用，断言变红。

### 验收

- 单测 **81 条**（+7：模糊归一 1、拼音四档 4、动态裕量 1、反向匹配 1）；jar 断言 **1193 条**。
- 变异：删掉界面报告可见行数 → 红；删掉拼音 token 访问器 → **编译失败**（状态机编译期就耦合住了）；
  `fuzzyKey` 变恒等 → 单测 I1/I4 红。
- 产物 md5（26.3 / 26.2 / 26.1.2 / 26.1.1 / 1.21.11）：
  `0713fe97 / 37b1c154 / 36f21dfd / 36362cb2 / 7c9e3caf`。

### ③ 列表高度：从按钮行向上反推（0.5.1 布局修复）

真机反馈：最后一行与底部按钮之间空了约 50px。两笔账：

- **固定预留**：`getBrowserHeight()` 写死 `screenHeight - 100`，而按钮行在 `screenHeight - 26`，
  列表底边 `44 + (H-100) = H - 56`，与按钮行顶边固定差 30px；
- **取整余数**：可见行数按 floor 取整，余下的不足一行（最多 23px）也成了空白。

修法：按「整行数」从按钮行向上反推。javap 实证 malilib 几何：
条目起点 = 列表顶边 + 27（搜索框 23 + browserPaddingY 4），滚动条底边 = 列表顶边 + browserHeight − 4。
所以 `browserHeight = 行数 × 24 + 31`（`WidgetListRecipe.CONTENT_OVERHEAD = 31`）时，
最后一行正好贴住列表底边：

    rows = (按钮行上方 4px 边界 − 列表顶边 − 31) / 24

界面给状态机的可见行数同步改成 `(browserHeight − 31) / 24` —— 以前的 `高度 / 24`
会把搜索框也算成一行，裕量因此虚高一行。

⚠️ **布局是视觉问题，字节码断言咬不住**（常量内联 + 断言只认字符串/引用）：这条只能真机验，
验收判据 = 最后一行贴住按钮行上方 4px。改动是布局修复，**版本号不动**（仍 0.5.1，原地重建）。

产物 md5（0.5.1 原地重建第 1 次，26.3 / 26.2 / 26.1.2 / 26.1.1 / 1.21.11）：
`f1cf1fc5 / 8d878713 / 0b79ea31 / 2d3ac666 / 1507c406`。

### ④ 「排序按钮没反应」的排查与一轮真机取证（0.5.1，2026-11-17）

真机反馈：点「排序」按钮毫无反应。静态排查把每一层都排完了，全部是通的：

- **malilib 路由（五版本 javap 全核对）**：`GuiListBase.onMouseClicked` 先调
  `GuiBase.onMouseClicked`，而后者**按钮最优先**（buttons → textFields → widgets）；
  `WidgetBase.onMouseClicked` 命中即 `onMouseClickedImpl`（放音效 + 调 listener）；
  `isMouseOver(int,int)` 是纯矩形判定，没有 visible/enabled 暗门。`ButtonGeneric`
  构造器不改几何 —— 画在哪判在哪。
- **状态机**：`setSort` 无 no-op（按钮按当前 sort 算出相反值）、`reload()` 在
  READY 态直接 `requestPage(0)`，50ms 限流只延一帧。
- **服务端**：`RecipeService.page` 对 `SORT_RECENT` 真的走倒序快照
  （`recipeSnapshot()` = `recipeTexts` 解码行序 = 学习序），与 id 序必然不同
  —— 只要点击生效，列表**一定**变。

每一层都对、合起来没反应 ⇒ 按纪律转真机取证，而不是继续猜：

1. `RecipeClientState.setSort` 加了审计日志（`[recipe] sort: 请求 X（当前 Y）`）——
   它是唯一分岔点：日志有 = 点击进了 listener；日志无 = 点击根本没到按钮
   （下一轮就要查输入层 / 其它按钮是否同样死）。
2. 顺手修了一个**真缺陷**：按钮文字是 `initGui` 时算死的，点击后永远不变 ——
   即使列表重排了，按钮还写着旧字样，玩家会先怀疑按钮坏了。现在点击 handler
   里即时 `setDisplayString`。

🔴 教训：**「按钮没反应」要先问「哪一类没反应」**——是点击没进（无日志无音效），
还是进了没效果（有日志、列表变没变）。按钮文字不更新本身就是独立的「看起来没反应」。
